# Методика вимірювання та порівняння методів

## 1. Вимірювання часу через DWT `CYCCNT`

Для програмних часових метрик використовується лічильник циклів DWT `CYCCNT`. Значення лічильника перетворюється у час через `SystemCoreClock`; часову шкалу розширено до 64 біт для уникнення проблеми переповнення 32-бітного лічильника. Метрики ініціалізуються після `App_Init()`, оскільки ініціалізація камери може впливати на DWT.

Для циклу та окремих задач збираються min/avg/max, кількість викликів, jitter і кількість пропущених періодів (`missed`). Навантаження обчислюється за інструментованими ділянками у вікнах 1000 мс.

## 2. Вимірювання логічним аналізатором

Сценарні файли `.sr` записані з частотою дискретизації 8 MHz. Доступні маркери:

- D0 / PC13 - фізичний вхід кнопки;
- D1 / PA4 - `App_RunOnce()`;
- D2 / PB0 - `ImuService_RunOnce()`;
- D3 / PB1 - обробка камери;
- D4 / PB10 - обробник кнопки.

Логічний аналізатор дає зовнішнє вимірювання сигналу на контакті та дозволяє побачити фактичні часові межі імпульсу. Частота 8 MHz відповідає кроку дискретизації 125 нс. Вона не гарантує такої самої точності кінцевої оцінки реакції, бо результат залежить від точок постановки GPIO-маркерів і способу декодування.

## 3. Порівняння двох методів для часу виконання

| Критерій            | DWT `CYCCNT`                                                                          | Логічний аналізатор                                                                                |
| ------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| Що вимірює          | Інтервал між програмними точками вимірювання                                          | Інтервал між фізичними фронтами GPIO                                                               |
| Перевага            | Можна вимірювати окремі функції без додаткових зовнішніх приладів                     | Незалежний зовнішній часовий контроль і видимість взаємного накладання сигналів                    |
| Обмеження           | Залежить від коректності `SystemCoreClock`, місця виклику та instrumentation overhead | Вимірює тільки те, що виведено на GPIO; результат залежить від частоти дискретизації та маркерів   |
| Наявні дані         | Є числові min/avg/max у `.log`                                                        | Є `.sr` на 8 MHz, але у наданому архіві немає підписаних числових інтервалів для зіставлення з DWT |
| Висновок порівняння | Внутрішні програмні метрики зібрано                                                   | Кількісне зіставлення двох методів ще не завершене                                                 |

**Не слід вигадувати коефіцієнт розбіжності двох методів.** Для завершення порівняння треба вибрати одну ділянку, наприклад `foreground_camera` або обробник кнопки, переконатися, що DWT і GPIO охоплюють ті самі початок/кінець операції, зняти однаковий тест, виміряти ширину імпульсу в PulseView і порівняти її з DWT-значенням.

## 4. Окреме застереження щодо latency кнопки

PB10 позначає ділянку обробника `UserButton_Process()` і вимірює її тривалість. Це не повна затримка реакції від натискання кнопки до зміни стану/індикації. Для end-to-end latency треба виміряти час від фронту PC13 до вихідної події, що точно відповідає завершенню реакції (наприклад, зміна стану або LED-маркер).

## 5. Обмеження інтерпретації

- `measured_work_load` - не повна апаратна утилізація CPU.
- `missed` показує пропущені планові виклики, але сам по собі не дає повного часу запізнення кожного запуску.
- Для наданих сценаріїв є один `.log` на сценарій; P99 та незалежні повтори не зафіксовані.
- У PRD немає числових вимог на максимальний час циклу або latency. Потрібно взяти їх із методички, якщо вони там задані.
