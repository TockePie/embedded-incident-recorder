## 2. Програмна конфігурація вимірювання

- Версія, записана у сценарних логах: `1.0.0`.
- Ідентифікатор збірки в заголовку логів: `git=PR10`. Це текстова мітка, а не повний Git SHA.
- Таймер вимірювань: DWT `CYCCNT`; цикл лічильника розширюється до 64-бітної часової шкали.
- Перерахунок тактів у час виконується через `SystemCoreClock`.
- Ініціалізація метрик виконується після `App_Init()`, оскільки ініціалізація камери може змінювати/скидати лічильник DWT.
- Вимірювання навантаження агрегується у вікнах 1000 мс і охоплює інструментовані робочі ділянки.

**Не зафіксовано у наданих артефактах:** точне числове значення частоти ядра під час тесту; повний Git commit SHA; конфігурація компілятора та прапорці оптимізації; окрема ознака Debug/Release. Ці значення треба взяти з фактичної збірки, а не припускати.

## 3. Періодичні та фонові задачі

| Задача         | Період |
| -------------- | -----: |
| button         |   5 мс |
| state_manager  |   5 мс |
| led            |  10 мс |
| cli            |   5 мс |
| config         |   5 мс |
| journal        |   5 мс |
| health_monitor | 100 мс |

Фонові ділянки, які мають окремі метрики: `foreground_camera` (`OV7670_DvpCapture_Process()`), `foreground_imu`, `foreground_detector`.

У доступному описі Super Loop вказано, що пропущені періодичні виклики рахуються як `missed`, а планувальник не виконує catch-up запуски для кожного пропущеного періоду. Формальні дедлайни задач у сценарних логах не наведені; їх потрібно підтвердити за вихідним кодом або методичкою.

## 4. Логічний аналізатор

У метаданих файлів `.sr` для сценаріїв S1–S3b зафіксовано частоту дискретизації **8 MHz** (крок вибірки 125 нс).

| Канал | Контакт | Призначення за описом вимірювань |
| ----- | ------- | -------------------------------- |
| D0    | PC13    | Фізичний вхід кнопки USER        |
| D1    | PA4     | Маркер `App_RunOnce()`           |
| D2    | PB0     | Маркер `ImuService_RunOnce()`    |
| D3    | PB1     | Маркер обробки камери            |
| D4    | PB10    | Маркер обробника кнопки          |

Важливе обмеження: імпульс PB10 вимірює тривалість роботи обробника кнопки, а не повну затримку від фізичного натискання до реакції системи. Для end-to-end latency треба виміряти інтервал від фронту PC13 до чітко визначеного вихідного сигналу/зміни стану.

## 5. Параметри пам'яті з окремого CLI-звіту

| Показник                         |                                                    Значення |
| -------------------------------- | ----------------------------------------------------------: |
| Внутрішня Flash                  | 131 852 / 524 288 байтів використано; 392 436 байтів вільно |
| Статична RAM (`data + bss`)      |                                     73 448 / 131 072 байтів |
| RAM після статичних даних        |                                                57 624 байти |
| Heap current / peak              |                                                0 / 0 байтів |
| Stack reserved                   |                                                 1 024 байти |
| Stack peak_used / free_watermark |                                            1 024 / 0 байтів |

Окремий `memory test` вивів `layout=PASS`, `heap_accounting=PASS`, `stack_paint=FAIL`. Команда `memory` в іншому діагностичному виводі показувала `paint=VALID`. Ці два результати не можна об'єднувати в однозначний висновок про справність стека: перевірку stack paint потрібно повторити й звірити з linker map та статичним аналізом `-fstack-usage`.

## 6. Умови, які треба дозаповнити перед фінальним звітом

- Повний Git SHA збірки замість мітки `PR10`.
- Фактичне значення `SystemCoreClock` під час тестування.
- Компілятор, версія toolchain, оптимізація, Debug/Release.
- Підтвердження, що instrumentation був увімкнений у всіх тестових запусках (наявність метрик це вказує, але конкретні compile flags не наведені).
- Формальні дедлайни задач, якщо вони відрізняються від періодів.
