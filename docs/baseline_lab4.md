# Базова лінія для ЛР4

Документ фіксує сценарії, метрики, гіпотези та вимірювальний інструментарій ЛР3 (bare metal / super loop), які в ЛР4 буде повторено на FreeRTOS. 

## 1. Порівняння ЛР3 ↔ ЛР4

1. Та сама апаратна платформа, той самий стенд, та сама швидкість UART і частота ядра.
2. Ті самі сценарії (розділ 3), та сама тривалість, той самий спосіб виклику подій.
3. Той самий вимірювальний інструментарій (розділ 2): DWT `CYCCNT`, службові GPIO, логічний аналізатор з частотою не нижче 8 МГц, команди CLI `metrics` / `memory`.
4. Максимум порівнюється з максимумом, а не середнє із середнім (середні майже не змінюються між сценаріями, максимуми змінюються на два порядки).
5. Лічильники `metrics` накопичуються від запуску пристрою і між сценаріями не скидаються. У ЛР3 S1, S2 і S3a знято на свіжих запусках (перші статуси на 47, 38 і 19 с після старту), а лог S3b охоплює весь час роботи з uptime_ms = 933 862 до 1 405 777 (1 422 вікна, 24 064 697 проходів) і включає S3a. Тому в ЛР4 перед кожним сценарієм слід перезапускати пристрій (або фіксувати `metrics` на початку й наприкінці та віднімати).
6. Умови прогону записуються поруч із результатом: збірка (повний Git SHA), `SystemCoreClock`, режим збірки, чи ввімкнено вимірювальний код.

## 3. Вимірювальний інструментарій

### 3.1. Команди CLI прошивки (USART1, 115200 8-N-1)

| Команда | Що робить | Використання |
| --- | --- | --- |
| `status` | Стан, режим, лічильники UART, `startup` | початок і кінець кожного сценарію |
| `config` | Поточна конфігурація, пороги, `sealed` | початок кожного сценарію |
| `metrics` | Час задач і foreground-операцій, цикл, джитер, `missed`, виміряне навантаження | кінець кожного сценарію |
| `metrics events` | Події FIFO метрик (до 32 за виклик; читання видаляє записи) | кінець кожного сценарію, до `metrics` для S3 |
| `memory` | Flash, RAM, heap, stack watermark | кінець кожного сценарію |
| `memory test` | `layout`, `heap_accounting`, `stack_paint` | один раз після збірки |
| `journal`, `photos` | Перегляд записів і фото | S2, S3a, S3b |
| `photo selftest`, `photo all` | Самоперевірка й передавання фото (через Host Tool) | S3b |

Формат рядків для розбору скриптом:

```text
[METRICS] <назва> n= min_us= avg_us= max_us= jitter_n= jitter_min= jitter_avg= jitter_max= missed=
[METRICS] loop count= min_us= avg_us= max_us=
[METRICS] measured_work_load current=<%> average=<%> max=<%> windows=
[METRICS] events queued= dropped=
[METRIC_EVENT] t_us= id=<назва> arg=            (для scheduler_missed: task= missed=)
[MEMORY] FLASH used= capacity= free= bytes
[MEMORY] RAM data= bss= static= capacity= free_after_static= bytes
[MEMORY] HEAP current= peak= capacity_to_stack_limit= min_reserve= sbrk_calls= failed= bytes
[MEMORY] STACK peak_used= reserved= free_watermark= bytes paint=VALID|INVALID
```
### 3.2. Службові GPIO та логічний аналізатор

| Канал | Пін | Що показує |
| --- | --- | --- |
| D0 | PC13 | Фізичний вхід кнопки USER |
| D1 | PA4 | Один прохід `App_RunOnce()` |
| D2 | PB0 | `ImuService_RunOnce()` |
| D3 | PB1 | `OV7670_DvpCapture_Process()` |
| D4 | PB10 | Обробка підтвердженого натискання в `AppTask_Button()` |

PA4, PB0, PB1, PB10 налаштовано як push-pull виходи, активний рівень HIGH. GND аналізатора з'єднується з GND плати, живлення з аналізатора на плату не подається. Файли записів: `docs/metrics/v1.0.0/*.sr`. У ЛР4 канали, піни та частоту дискретизації слід лишити без змін (для задач FreeRTOS маркери PA4/PB0/PB1 переносяться на відповідні задачі, а сенс каналів фіксується в описі прогону).

## 4. Сценарії та як їх відтворити

### S1. Простій

| Поле | Опис |
| --- | --- |
| Мета | Базові значення циклу, навантаження, пропусків без інцидентів |
| Початкові умови | `startup=PASS`, режим `CARGO`, стан `DISARMED`, конфігурацію не запечатано |
| Кроки | 1. Подати живлення. 2. `status`, `config`. 3. Залишити систему в `DISARMED`, без подій. 4. Знімати запис аналізатора. 5. Наприкінці `metrics`, `metrics events`, `memory`. |
| Тривалість | ≈ 57,44 с між першим і останнім статусом (за різницею `uptime_ms`). Точну тривалість запису [УТОЧНИТИ] |
| Повтори у ЛР3 | 1 (`S1_idle.log`, `S1_idle.sr`) |
| Критерій | `DISARMED`, `startup=PASS`, `events dropped=0` |

### S2. Номінальний (Cargo)

| Поле | Опис |
| --- | --- |
| Мета | Штатні інциденти Cargo, перемикання станів, фото |
| Початкові умови | `startup=PASS`, `CARGO`, `DISARMED`, пороги з конфігурації запуску [УТОЧНИТИ значення порогів] |
| Кроки | 1. `status`, `config`. 2. Кнопкою перевести систему в `ARMED`. 3. Контрольованими діями викликати SHOCK, TILT, TEMPERATURE (спосіб дії та кількість повторів [УТОЧНИТИ]). 4. Перевірити записи та фото (`journal`, `photos`). 5. Кнопкою повернути в `DISARMED`. 6. `metrics`, `metrics events`, `memory`. |

| Повтори у ЛР3 | 1 (`S2_nominal.log`, `S2_nominal.sr`) |
| Критерій | У журналі є SHOCK, TILT, TEMPERATURE; послідовність станів містить `ARMED` і `DISARMED` |

### S3a. Найгірший випадок: часті повторні інциденти

| Поле | Опис |
| --- | --- |
| Мета | Поведінка за частих повторних SHOCK і підвищеного навантаження на фотографування |
| Початкові умови | `startup=PASS`, `CARGO`, `DISARMED`; поріг SHOCK 1000 мг |
| Кроки | 1. `status`, `config`. 2. Перейти в `ARMED`. 3. Створювати повторні механічні впливи вище порога (кількість і частота [УТОЧНИТИ]). 4. Спостерігати записи SHOCK, фото, cooldown. 5. Повернути в `DISARMED`. 6. `metrics`, `metrics events`, `memory`. |
| Тривалість | ≈ 206,46 с |
| Повтори у ЛР3 | 1 (`S3a_worst_case.log`, `S3a_worst_case.sr`) |
| Критерій | Є SHOCK-події і записи cooldown; метрики зібрано; UART-лічильники помилок нульові |

### S3b. Передавання фото по UART

| Поле | Опис |
| --- | --- |
| Мета | Отримання збережених фото через CLI та стійкість до сторонніх байтів |
| Початкові умови | `startup=PASS`, `CARGO`, `DISARMED`, USART1 115200 8-N-1; у пам'яті 75 фото |
| Кроки | 1. `photos` (перелік). 2. `photo all` через `ir_host`. 3. Перевірити кількість і CRC32 на хості. 4. `photo selftest`. 5. `metrics`, `metrics events`, `memory`, `status` (лічильники UART). |
| Тривалість | ≈ 471,92 с між статусами (не чистий час передавання) |
| Повтори у ЛР3 | 1 (`S3b_photo_transfer.log`, `S3b_photo_transfer.sr`) |
| Увага | Метрики в `S3b_photo_transfer.log` накопичені від запуску і включають S3a; внесок самого S3b — приріст відносно S3a (п. 5.6) |
| Критерій | 75/75 фото, `photo selftest=PASS`, UART-лічильники помилок = 0 |

> У методичці S3 — один сценарій «усе одночасно». У ЛР3 його розділено на S3a і S3b. У ЛР4 розділення слід зберегти. Сценарій «усе одночасно» (довга операція + інциденти + потік команд + подія) в ЛР3 не виконувався.

## 5. Базові значення метрик (S1–S3b)

## 6. Гіпотези для ЛР4

| № | Обмеження | Базове значення | Очікувана зміна на FreeRTOS | Метрика для перевірки |
| --- | --- | --- | --- | --- |
| 1 | Довга ділянка камери (LIM-01) | `foreground_camera` max 95 088 мкс; `loop` max до 101 056 мкс | Крок камери в окремій задачі не затримує інші: максимальний час проходу/джитер перестають залежати від тривалості кроку камери | `loop`/задачі max, `jitter_max`, `missed` у S2–S3b |
| 2 | Пропуски і джитер періодичних задач (LIM-02) | `missed` 3 / 102 / 248 / 254; `button` jitter max 11 746 → 96 342 | `missed` для задач 5 мс має наблизитися до нуля в S3a/S3b | `button` missed, `button` jitter max |
| 3 | Затримка реакції на кнопку (LIM-10) | Не виміряна; оцінка ≈ 136 мс | Затримка визначається debounce і перемиканням контексту, а не тривалістю кроку камери | PC13 → зміна стану (аналізатор) |
| 4 | Переповнення RX UART (розрахунок) | Не виміряно; розрахунок ≈ 11 мс до заповнення 127 Б при 11 520 Б/с; окрема сесія `rx_overflow=247` | При тому самому буфері `rx_overflow` зменшується або зникає | `rx_overflow` у сценарії UART flood |
| 5 | Блокувальні транзакції (I²C 25 мс, SPI 100 мс, діагностичний UART 1000 мс) | Не виміряно | При відмові сенсора джитер інших задач 5 мс не зростає до тайм-ауту I²C | джитер задач під час відмови сенсора |
| 6 | Втрата діагностичних подій (LIM-03) | `events dropped` 0 / 9 / 417 / 417 | Кількість втрачених подій зменшується за тієї самої інтенсивності | `events dropped` у S3a/S3b |
| 7 | Невизначений запас стека (LIM-04) | peak = reserved = 1 024 Б, `stack_paint=FAIL` | Сумарна RAM (статична + стеки задач) зростає; запас кожного стека вимірюється високою водяною позначкою | RAM static, stack high-water mark по задачах |

Очікуване збільшення витрат на ОС (гіпотеза): зростання використання RAM (поточна статична RAM 56,0 %), накладні витрати перемикання контексту, нові класи помилок (інверсія пріоритетів, взаємні блокування на SPI-шині Flash, переповнення стека задачі).

## 7. Що super loop робить краще (перевірити в ЛР4)

| Властивість | Базове значення | Що перевірити на RTOS |
| --- | --- | --- |
| Передбачуваність середнього проходу | `loop` avg 49–52 мкс, min 30 мкс | Накладні витрати планувальника та перемикання контексту |
| Економія пам'яті | Heap = 0; Flash 25,1 %; static RAM 56,0 % | Збільшення Flash/RAM після додавання ядра, стеків задач, черг |
| Простота налагодження | Лінійний `App_RunOnce()` | Складність налагодження переривань і гонок (якісна оцінка) |
| Час старту | Не виміряно (`boot.log`: `SELF-TEST: PASS`, `SYSTEM: READY`) | Виміряти час від живлення до першого коректного виміру для обох реалізацій |
