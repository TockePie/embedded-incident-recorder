# Метрики

## 1. Призначення

Модуль метрик забезпечує вимірювання часу виконання головного циклу, задач планувальника та окремих операцій основного циклу, оцінювання періодичності запуску задач, облік пропущених періодів, оцінювання завантаження CPU за вимірюваними ділянками коду, журналювання подій, а також оцінювання використання Flash, RAM, Stack і Heap.

Для вимірювання часу використовується лічильник тактів ядра DWT `CYCCNT`. Значення лічильника розширюється до 64-бітної часової шкали; частота ядра береться з `SystemCoreClock`. Ініціалізація метрик виконується після `App_Init()`, оскільки ініціалізація камери може використовувати та скидати `DWT->CYCCNT`.

Для зовнішнього спостереження за тривалістю головного циклу та окремих операцій використовуються службові GPIO.

## 2. Час виконання задач та операцій

Для кожної інструментованої задачі або операції збираються кількість вимірювань, мінімальний, середній і максимальний час виконання. Час виводиться в мікросекундах.

| Назва | Призначення | Налаштований період |
|---|---|---:|
| `button` | Обробка кнопки B1 | 5 мс |
| `state_manager` | Обробка переходів стану системи | 5 мс |
| `led` | Оновлення індикації | 10 мс |
| `cli` | Обробка командного інтерфейсу | 5 мс |
| `config` | Обробка конфігурації та обслуговування сховища | 5 мс |
| `journal` | Обробка журналу інцидентів, фото та сервісу захоплення | 5 мс |
| `health_monitor` | Періодичний контроль стану системи | 100 мс |
| `foreground_camera` | Обробка стану захоплення кадру `OV7670_DvpCapture_Process()` у головному циклі | Не періодична задача |
| `foreground_imu` | Отримання та обробка даних MPU-6050 у головному циклі | Не періодична задача |
| `foreground_detector` | Обробка вимірювання та виявлення інцидентів у головному циклі | Не періодична задача |

Для кожної задачі або операції виводяться такі показники:

| Метрика | Поле | Опис |
|---|---|---|
| Кількість вимірювань | `n` | Кількість виміряних запусків. |
| Мінімальний час | `min_us` | Найменша тривалість виконання, мкс. |
| Середній час | `avg_us` | Середня тривалість виконання, мкс. |
| Максимальний час | `max_us` | Найбільша тривалість виконання, мкс. |

Статистика виводиться командою `metrics`. Для кожної задачі або операції використовується рядок такого формату:

```text
[METRICS] <назва> n=<кількість> min_us=<мінімум> avg_us=<середнє> max_us=<максимум> jitter_n=<кількість інтервалів> jitter_min=<мінімум> jitter_avg=<середнє> jitter_max=<максимум> missed=<пропущені періоди>
```

Для операцій `foreground_camera`, `foreground_imu` та `foreground_detector` періодичний джитер не обчислюється, оскільки для них передається `period_ms = 0`. Для таких операцій поля джитеру та `missed` не мають змістовного значення.

## 3. Тривалість головного циклу

Для повного проходу `App_RunOnce()` збираються кількість виміряних проходів, мінімальна, середня та максимальна тривалість. Вимірювання починається перед викликом `App_RunOnce()` і завершується після його повернення.

Результат виводиться командою `metrics` у форматі:

```text
[METRICS] loop count=<кількість> min_us=<мінімум> avg_us=<середнє> max_us=<максимум>
```

Поле `count` показує кількість виміряних проходів головного циклу. Час охоплює виконання `App_RunOnce()`, зокрема foreground-операції та запуск задач планувальника, але не включає виклики `Metrics_LoopBegin()`, `Metrics_LoopEnd()` і `Metrics_Poll()` поза межами вимірюваного інтервалу.

## 4. Джитер періодичних задач і пропущені періоди

Джитер визначається як різниця між фактичним інтервалом між початками двох послідовних запусків задачі та її заданим періодом:

```text
jitter = фактичний інтервал між стартами − заданий період
```

| Метрика | Поле | Опис |
|---|---|---|
| Кількість інтервалів | `jitter_n` | Кількість інтервалів між послідовними запусками, для яких обчислено джитер. Перший запуск не утворює інтервалу. |
| Мінімальний джитер | `jitter_min` | Найменше відхилення фактичного інтервалу від заданого періоду, мкс. |
| Середній джитер | `jitter_avg` | Середнє відхилення, мкс. |
| Максимальний джитер | `jitter_max` | Найбільше відхилення, мкс. |
| Кількість пропущених періодів | `missed` | Сумарна кількість періодів, пропущених планувальником для задачі. |

Джитер обчислюється для семи періодичних задач: `button`, `state_manager`, `led`, `cli`, `config`, `journal` і `health_monitor`.

Планувальник не відтворює пропущені запуски серією наздоганяючих викликів. Якщо з моменту попереднього запуску минуло більше одного періоду, він виконує задачу один раз, оновлює час останнього запуску та обліковує кількість пропущених періодів за формулою:

```text
missed_periods = floor(фактичний інтервал / заданий період) − 1
```

Значення `missed` у звіті є накопичувальним лічильником пропущених періодів, а не кількістю всіх інтервалів, що просто перевищили два періоди.

## 5. Реакція на кнопку B1

Окрема числова статистика затримки реакції на кнопку в поточній реалізації не формується. Обробка кнопки `UserButton_Process()` виконується періодично задачею `button` з періодом 5 мс. Коли функція фіксує натискання після програмної обробки кнопки, активується службовий GPIO PB10 на час обробки події в `AppTask_Button()`.

Отже, імпульс PB10 дає змогу спостерігати тривалість ділянки обробки підтвердженого натискання, але не є вимірюванням затримки від переривання до реакції в головному циклі. Поля `btn_latency`, `min_us`, `avg_us` і `max_us` для окремої метрики кнопки в CLI не виводяться.

## 6. Завантаження CPU

Завантаження CPU є оцінкою частки часу вимірювального вікна, витраченої на виконання інструментованих ділянок коду. Тривалість цих ділянок додається до лічильника зайнятого часу.

Вимірювання виконується у вікнах тривалістю 1000 мс. У чисельнику враховуються виміряні callback-и семи задач планувальника та три foreground-операції: `foreground_camera`, `foreground_imu` і `foreground_detector`.

| Метрика | Поле у звіті | Опис |
|---|---|---|
| Завантаження останнього вікна | `current` | Відсоток часу останнього завершеного вікна, витрачений на вимірювані ділянки. |
| Середнє завантаження | `average` | Середнє відношення сумарного виміряного часу роботи до сумарного часу вікон. |
| Максимальне завантаження | `max` | Найбільше зафіксоване значення. |
| Кількість вікон | `windows` | Кількість оброблених вікон вимірювання. |

Звіт є частиною виводу команди `metrics`:

```text
[METRICS] measured_work_load current=<значення>% average=<значення>% max=<значення>% windows=<кількість>
```

Це **не повне апаратне завантаження CPU**. До чисельника не входять перевірки готовності задач у планувальнику, службова логіка super loop та час необлікованих обробників переривань. Якщо переривання відбувається всередині вимірюваної ділянки, його тривалість входить до wall-time цієї ділянки. Тому показник слід трактувати як оцінку навантаження за інструментованими ділянками програми.

## 7. Журнал подій

Журнал подій реалізований як кільцевий FIFO-буфер місткістю 64 записи. Кожен запис містить ідентифікатор події, аргумент і часову мітку в тактах DWT. Під час переповнення найстаріший запис витісняється, а лічильник `dropped` збільшується.

У поточній реалізації реєструються такі події:

| Назва події | Значення | Аргумент |
|---|---|---|
| `button_press` | Зафіксоване натискання B1 | Поточний стан системи на момент обробки натискання. |
| `state_change` | Зміна стану системи | Попередній стан у старших 16 бітах і новий стан у молодших 16 бітах. |
| `incident_count` | Зміни загальної кількості виявлених інцидентів | Поточна сумарна кількість подій детектора. |
| `fault_entered` | Перехід системи у стан FAULT | Код помилки. |
| `scheduler_missed` | Пропущені періоди задачі планувальника | Ідентифікатор задачі у старших 8 бітах і кількість пропущених періодів у молодших 24 бітах. |

Події читаються командою `metrics events`. На один виклик команди виводиться не більше 32 записів; якщо у FIFO залишилися записи, CLI повідомляє про залишок і пропонує виконати команду повторно. Читання видаляє записи з FIFO.

Формат звіту:

```text
[METRICS] events queued=<кількість> dropped=<кількість>
[METRIC_EVENT] t_us=<час> id=<назва> arg=<аргумент>
```

Для події `scheduler_missed` замість загального аргументу виводяться назва задачі та кількість пропущених періодів:

```text
[METRIC_EVENT] t_us=<час> id=scheduler_missed task=<назва задачі> missed=<кількість>
```

Події `cmd_rx`, `cmd_done`, `capture_start`, `capture_done`, `flash_start` і `flash_done` у поточній реалізації цього модуля не реєструються.

## 8. Використання стека

Використання стека оцінюється методом stack painting. На самому початку `main()`, до виклику `HAL_Init()`, зарезервована linker-ом область MSP Stack заповнюється контрольним шаблоном. Під час формування звіту аналізується, яка частина шаблону була перезаписана.

| Метрика | Поле у звіті | Опис |
|---|---|---|
| Пікове використання стека | `peak_used` | Оцінений максимальний обсяг використання стека від моменту запуску, байти. |
| Зарезервований розмір | `reserved` | Розмір області `_Min_Stack_Size` з активного linker script, байти. |
| Вільний залишок за watermark | `free_watermark` | Зарезервований розмір мінус оцінене пікове використання, байти. |
| Стан фарбування | `paint` | `VALID`, якщо початкове заповнення області виконано коректно; інакше `INVALID`. |

Результат виводиться командою `memory`:

```text
[MEMORY] STACK peak_used=<байти> reserved=<байти> free_watermark=<байти> bytes paint=VALID
```

Вимірювання охоплює лише linker-зарезервовану область `_Min_Stack_Size`, а не довільно всю SRAM. Під час фарбування зберігається 64-байтовий запас біля поточного покажчика стека. Початково зайнята область також враховується як використана. Сам виклик `memory` може збільшити watermark, оскільки його власні кадри функцій використовують той самий стек.

Watermark є оцінкою фактичного використання в уже виконаних сценаріях, а не доказом того, що стек не переповниться в усіх можливих сценаріях. Якщо вільний залишок малий, необхідно збільшити резерв стека в активному linker script і повторити вимірювання.

## 9. Звіт про Flash, RAM і Heap

Команда `memory` виводить також оцінки використання внутрішньої Flash, статичної RAM та Heap.

### Flash

Використання Flash обчислюється за linker-символами: від початку внутрішньої Flash (`0x08000000`) до кінця завантажувального образу секції `.data`. Для STM32F411RE місткість внутрішньої Flash становить 512 KiB. Зовнішня SPI Flash W25Q64 до цього показника не входить.

```text
[MEMORY] FLASH used=<байти> capacity=<байти> free=<байти> bytes
```

Це оцінка за linker-символами; остаточний розмір зібраного образу слід також перевіряти за ELF та map-файлом.

### RAM

Окремо виводяться розміри секцій `.data` та `.bss`, статичний діапазон RAM від `0x20000000` до linker-символу `_end`, загальна місткість SRAM і залишок після статичних даних. Для STM32F411RE місткість SRAM становить 128 KiB.

```text
[MEMORY] RAM data=<байти> bss=<байти> static=<байти> capacity=<байти> free_after_static=<байти> bytes
```

`free_after_static` — це залишок адресного простору RAM після статичних секцій та інших розміщених перед `_end` даних. Це не тотожне вільному Heap: з цього простору ще потрібно враховувати обмеження, пов'язані з Heap і зарезервованою областю Stack.

### Heap

Облік Heap виконується в реалізації `_sbrk()` для newlib. Відстежуються поточний і піковий обсяг запитаного через `_sbrk` простору, місткість до межі зарезервованої області Stack, мінімальний резерв Heap із linker script, кількість викликів `_sbrk` та кількість невдалих запитів.

```text
[MEMORY] HEAP current=<байти> peak=<байти> capacity_to_stack_limit=<байти> min_reserve=<байти> sbrk_calls=<кількість> failed=<кількість> bytes
```

Якщо програма не використовує динамічне виділення пам'яті, очікуваними значеннями є `sbrk_calls=0`, `current=0` і `peak=0`; це саме по собі не є помилкою. Пікове значення відображає максимальний обсяг, до якого зростав break через `_sbrk`, а не суму активних блоків `malloc()`. Звільнення пам'яті через `free()` не обов'язково зменшує break.

## 10. Підключення логічного аналізатора

Під час тестування використовувалися п'ять каналів логічного аналізатора. D0 підключався до фізичного входу кнопки USER, а D1–D4 — до службових GPIO-виходів, які формують часові маркери виконання програмних ділянок.

| Канал аналізатора | Пін STM32 | Призначення |
|---|---|---|
| D0 | PC13 | Фізичне натискання USER button. Це вхід кнопки, а не службовий GPIO-вихід модуля метрик. |
| D1 | PA4 | Повний прохід `App_RunOnce()` — один прохід головного циклу. |
| D2 | PB0 | Виконання `ImuService_RunOnce()` — foreground-обробка MPU-6050. |
| D3 | PB1 | Виконання `OV7670_DvpCapture_Process()` — foreground-обробка камери. |
| D4 | PB10 | Обробка підтвердженого натискання кнопки в `AppTask_Button()`. |

PA4, PB0, PB1 і PB10 налаштовуються як виходи push-pull. Їхній активний рівень HIGH позначає відповідну інструментовану ділянку, а ширина імпульсу показує її тривалість. PC13 залишається входом фізичної кнопки USER; він дає змогу зіставити момент натискання з подальшою програмною обробкою, позначеною імпульсом D4 на PB10. D4 не є окремим вимірюванням затримки від переривання до реакції: він показує лише тривалість ділянки обробки вже підтвердженого натискання.

Для вимірювань потрібно з'єднати GND логічного аналізатора із GND плати. Входи аналізатора мають бути високого імпедансу; подавати живлення з аналізатора на плату не потрібно.

## 11. Ініціалізація модуля

На початку `main()` викликається `MemoryMetrics_StackPaint()` — до `HAL_Init()`. Після `MX_GPIO_Init()` налаштовуються службові GPIO через `Metrics_ProbeInit()`. Після ініціалізації периферії та `App_Init()` викликається `Metrics_Init()`, який вмикає DWT `CYCCNT` і скидає внутрішні лічильники метрик.

У головному циклі вимірювання одного проходу оточує `App_RunOnce()` викликами `Metrics_LoopBegin()` і `Metrics_LoopEnd()`. Після завершення проходу викликається `Metrics_Poll()`, який оновлює розширену часову шкалу та обробляє вікно завантаження.

Окреме початкове повідомлення виду `METRICS fw=<версія> clk=<частота> Hz probes=...` поточною реалізацією не виводиться.

## 12. Підсумок команд і повідомлень із метриками

| Команда / повідомлення | Що містить | Джерело |
|---|---|---|
| `metrics` — `measured_work_load` | Поточна, середня та максимальна оцінка вимірюваного навантаження, кількість вікон | `Cli_PrintMetrics()` / `Metrics_LoadStatsGet()` |
| `metrics` — `loop` | Кількість проходів головного циклу та мінімальний, середній і максимальний час | `Metrics_LoopStatsGet()` |
| `metrics` — рядки задач і foreground-операцій | Кількість, мінімальний, середній і максимальний час; статистика джитеру та пропущених періодів | `Metrics_ExecStatsGet()` |
| `metrics events` | Кількість записів у FIFO, кількість витіснених записів, часові мітки та події | `Metrics_EventStatusGet()` / `Metrics_EventPop()` |
| `memory` — `FLASH` | Використана, загальна та вільна внутрішня Flash | `MemoryMetrics_GetSnapshot()` |
| `memory` — `RAM` | `.data`, `.bss`, статичний обсяг RAM і залишок після статичних даних | `MemoryMetrics_GetSnapshot()` |
| `memory` — `HEAP` | Поточний і піковий обсяг `_sbrk`, місткість до межі Stack, лічильники запитів | `MemoryMetrics_GetSnapshot()` / `_sbrk()` |
| `memory` — `STACK` | Пікове використання, зарезервований розмір, watermark вільного залишку та стан фарбування | `MemoryMetrics_GetSnapshot()` |
| `memory test` | Результати перевірок linker layout, stack painting та обліку Heap | `MemoryMetricsTest_Run()` |

Команда `memory test` не виконує `malloc()` і не змінює стан продукту. Вона перевіряє коректність linker-діапазонів, доступність stack painting і узгодженість лічильників Heap. У звіті `MEMORY_TEST` кожна з трьох перевірок має статус `PASS` або `FAIL`.

Для додаткового аналізу використання стека на рівні окремих функцій під час компіляції можна ввімкнути прапорці GCC `-fstack-usage` та `-Wstack-usage=512`. Скрипт `tools/summarize_stack_usage.py` формує зведення за створеними компілятором файлами `.su`. Цей статичний звіт є додатковим засобом аналізу і не замінює runtime stack watermark.
